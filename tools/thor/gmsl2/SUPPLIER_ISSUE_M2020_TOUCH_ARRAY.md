# M2020 触觉贴片 3x3 逐点数组读数与设备自报总力不一致

## 问题摘要

我们在 Jetson Thor 上通过 BOX SDK（`box-collection-sdk` wheel，当前 `0.1.0`）读取贴装 M2020（3x3，9 点）触觉贴片的 `TouchSensor` 数据。同一帧内，SDK 报出的逐点数组（`fx_0p1N`/`fy_0p1N`/`fz_0p1N`，9 槽）与同一帧一起报出的 `total_force_0p1N`（贴片总力）经常互相矛盾：逐点数组要么整帧跳到一组完全不相邻的槽位上，要么整帧归零，而 `total_force_0p1N` 在同一时刻保持连续、平滑，且与我们独立测得的 6D 力传感器（贴片所在关节的六维力/力矩）走向一致。

现象更像是逐点数组在读出/打包路径上被破坏（索引错位、多路复用串扰或缓冲区竞争），而不是传感器物理响应或我们主机侧解析问题——因为同一次采样里，设备自己算出来的总力从未跟着一起跳变。

## 环境信息

```text
Jetson 平台: Thor
BOX SDK wheel: box-collection-sdk 0.1.0（自包含 aarch64 wheel，2026-08 部署）
触觉贴片型号: M2020，3x3 = 9 taxel
BOX 型号 / box_id 示例: box1672693301, box1819152274（同型号两台，现象一致）
链路识别: link stream tlv_type 0x0008/0x0009（M2020），SDK 侧已按此正确截断为 9 槽
采样率: 触觉 ~58-60 Hz，6D 力传感器 ~471-476 Hz（同一 BOX 上）
```

## 现象 1：逐点数组在单帧内整片跳到不相交的槽位组

以 `box1819152274/box_touch_left`（episode 2）为例，`t=4.183s` 这一帧相对上一帧（`t=4.166s`，间隔 16.68 ms，采样间隔正常、无丢包）：

```text
t=4.166  fz(0..8)=[  0   0   0   0  79  29   0  29   0]  sum=137  total_force_0p1N[z]=86
t=4.183  fz(0..8)=[  2   3   0   5   0   0   0   0   0]  sum=10   total_force_0p1N[z]=91
```

逐点数组的支撑集从 `{4,5,7}` 完全跳到 `{0,1,3}`（互不相交），逐点求和从 137 掉到 10（0.1N 单位，跌了 12.7 N），但同一帧 `total_force_0p1N[z]` 是 86 -> 91，**继续单调上升，没有任何异常**。前后 0.12 s 窗口内我们独立采集的 6D 力传感器读数变化 ≤0.6 N。人的手指不可能在 16.7 ms 内卸掉 12.7 N 又立刻加回同等负载，而 6D 力传感器也没有观测到任何负载突变——因此这次跳变只能是逐点数组的读出问题。

这批数据里一共采到 7 次类似的整片跳变，逐帧数据见附带的 `m2020_hard_switches_20260824.csv`（7 行，每行一次跳变，含时间戳、MCU 时间戳间隔、跳变前后支撑集、跳变前后 `total_force_0p1N`、跳变前后 6D 力差）。

## 现象 2：持续加载中逐点数组会整帧归零，同时 total_force 报出接近满量程

例如同一贴片 `episode 2` 里，`t=15.433~15.467s` 这三帧连续：

```text
t=15.433  fz(0..8)=全 0   sum=0   total_force_0p1N[z]=255（满量程 25.5N）
t=15.449  fz(0..8)=全 0   sum=0   total_force_0p1N[z]=255
t=15.467  fz(0..8)=全 0   sum=0   total_force_0p1N[z]=255
```

即在设备自己报出「贴片顶格受力 25.5 N」的同一时刻，9 槽逐点数组连续三帧全部归零。这类「数组全零但 total_force 明显非零」的帧在这批数据里共出现约 8-20 帧/贴片，且 **100% 落在已知的按压窗口内**（不是真空闲段）——也就是说，逐点数组的「归零」不能作为「无接触」的判据，它在真实持续接触期间也会发生。

## 现象 3（供参考，暂不确定是否与上述同一根因）：单点按压时中心槽（idx4）系统性地读数最高

我们做了逐角点单独按压（每次仅按压 3x3 网格的一个角）。16 次角点按压中，**16 次的峰值帧 argmax 都落在中心槽（idx4）**，四角槽（idx0/2/6/8）合计仅占该帧总力的 0-8.8%（11/16 次角点槽合计恰好为 0）。这个现象在按压期间用肉眼实时观察 GUI 也能直接复现，与录制数据完全吻合，暂不确定是贴片本身的力学设计（例如顶盖经中心支撑结构传力）还是与现象 1/2 同源的读出问题，希望供应商一并确认。

## 请供应商协助确认

1. `fx/fy/fz_0p1N`（逐点 9 槽）与 `total_force_0p1N` 在固件/ASIC 内部是否来自同一次采样、同一条流水线？如果 `total_force` 是在逐点数组「之前」的更早阶段算出（例如模拟域求和），而逐点数组是后级 ADC 多路复用/数字化的结果，那么现象 1/2 很可能是多路复用器串扰或数字化时序问题，不影响求和环节。
2. 是否存在已知的 I2C/SPI/UART 多路复用竞争、DMA 缓冲区未同步、或槽位索引在特定负载/温度条件下错位的问题？
3. 逐点数组的采样是否严格同步（9 槽同一时刻采样）还是分时轮询（9 槽依次读出，跨越若干 ms）？如果是分时轮询，负载快速变化时槽位错位或许可以解释部分（但不能解释 16.7 ms 内的整片跳变，那已经小于一次上报周期）。
4. 现象 3（角点按压时中心槽读数最高）是否符合贴片的机械/力学设计预期？如果是，能否提供顶盖/支撑结构的示意图或标定曲线，帮助我们校正下游的定位算法。
5. 是否有更高分辨率（当前逐点 fz 是 uint8，0.1N 单位，25.5N 顶格）或原始 ADC 读数可选，便于我们独立诊断？

## 我们目前的规避方案

在下游只使用设备自报的 `total_force_0p1N`（含其自身的 uint8 饱和标志）作为可信触觉信号，逐点 9 槽数组仅作诊断展示，不进入统计或训练特征，直到上述问题定位清楚。
