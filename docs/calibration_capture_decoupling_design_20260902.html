Calibration · 采集架构设计

标定采集解耦设计

内参是 11 个独立的单相机问题，外参是 1 个 11 体联合问题。代码里这句话写对了，数据里没有——两者至今共用同一个 recorder、同一个 dataset root、同一份 11 路视频。这份文档给出把它们拆开的四层方案，以及为什么其中第二层修的是一个正在静默发生的正确性问题。

01

三个问题的答案

全部对照 HEAD 复核过

内参段也是 11 路一起录吗？

是 一路不少。

标定向导没有自己的录制器。gateway.py:3583 _calibration_step_record("start") 直接调 _start_episode，和 Live Record 按 StartEpisode 是同一个函数。

内外参数据集分开了吗？

解算分了，采集没分

解算侧有 intrinsicsDatasetRoot / solveDatasetRoot 两个独立指针 gateway.py:5004；采集侧只有 Connect 时绑定的那一个 root。

能与 Live Record 解耦吗？

能，而且不解耦正在制造 bug。

关键是 ep_dir 在每个 episode 循环里现算 thor_record.py:1642——换 dataset root 根本不需要碰 Argus。

02

第一性：这是两类结构不同的问题

内参外参
问题结构N 个独立的单相机问题1 个 N 体联合问题
约束来源板子走到这一台的画幅多靠边多台同时看到同一块板
其他相机的贡献恒为零是全部
操作距离0.5–0.8 m（A 板 marker 成像 25–45 px）桌面中部上方，走遍作业区
最小充分采集单元1 路 × TN 路 × T
现在实际采集11 路 × T（11× 过采集）11 路 × T ✓
这条结论代码里已经写对了

CalibrationStep 的 docstring gateway.py:276：

Intrinsics need one sweep per camera because the binding constraint is how much of that camera's frame the board reaches; extrinsics need a single sweep that several cameras see at once, because the constraint is co-visibility. They cannot share a capture.

操作指引写得更直白 calibrationGuide.ts:20：「只面对当前这一台相机，其余相机此刻不用管——内参是逐台标的」。

设计意图从一开始就是逐台的。只有管线是全集的。那句 "cannot share a capture" 落实到了「分成不同的 step」，没有落实到「分成不同的数据」。

04

耦合的六项代价

按严重度排序，不是按大小
01

内参拟合吃进了协议明确排除的帧

正确性 · 静默

calibrate_intrinsics.py:99 按相机名把所有 episode 的 npz 合并：

by_camera.setdefault(path.stem.split("__")[1], []).append(path)

于是 cam_05 的内参拟合，吃进去的不只是「操作员站在 cam_05 前 0.5–0.8 m 挥板」那一段，还有另外 10 段里 cam_05 恰好瞄到板子的帧。那些帧的距离、角度、模糊程度全在指引明确判定为不可靠的区间之外——B 板在 1.2 m 处实测检出 0/63，A 板也要求 0.5–0.8 m。

02

验收判据被同一批帧顶过门槛

共模盲区

observed_radius_fraction gateway.py:5571 是在上面那个合并集合上算的。后果是：一台相机自己那段挥得不合格，靠别人挥板时蹭到的边角帧把覆盖率顶过门槛，就会静默通过。

这不是假设。0804 那轮标定第一次就是栽在覆盖率上——48–71%，畸变拟合在自己画幅内折返，整份采集重录；重录后 cam_08 从 62% 提到 96%。而验收判据本身能被别的段的帧污染，意味着下一次同样的失败可能不会被拦下来。

结构上，这与之前 cube 晃动那类问题同构：判据和被判对象共享同一个被污染的输入，所有既有检查同时失效。

03

标定段被算成任务进度，并会被导进 v3 训练集

数据污染

如果 Connect 时绑定了 active task，dataset root 就是那个任务的训练数据集。于是 12 段挥板：

  • _count_completed_episodes gateway.py:6045 按目录名前缀统计，标定段被算成任务进度
  • _export_command 按同样的名字前缀合并所有 session，标定段会被导进 v3 训练集

06

一条「结构性不可能」其实是耦合的产物

假阳性

_intrinsics_preflight gateway.py:5096 的注释断言：

cam_02/cam_03 point away from the board area and detect nothing in every episode, which makes "re-fit and export from a full-rig capture" structurally impossible rather than unlucky

但 _capture_cameras gateway.py:5091 的定义是「采集里有视频的相机」。cam_02/cam_03 出现在内参采集里，纯粹是因为它们被顺带录进去了——操作员从来没打算给它们标内参。内参采集只包含被扫过的相机之后，这条 preflight 就不会因为「顺带录进来的相机」而拦截。

要说明清楚：导出器无法从在产 run 承接未重拟的相机，这是另一条真实的结构性缺口，解耦不解决它。解耦之后 preflight 触发时才是真信号，缺口本身要单独补（见落地顺序第 4 项）。

07

provenance 只活在内存里

可审计性

CalibrationSession gateway.py:292 是纯内存 dataclass。「episode 7 是 cam_05 的内参段」这条信息只存在于 step.episodeIndex。网关一重启、向导一 cancel，磁盘上就是 12 个无法区分的 episode。

05

设计：四层，加一层缓议

每层独立可上线，收益递减、风险递增
关键约束，以及为什么它不挡路

Argus 会话必须一次开好。nvargus-daemon 的不稳定、spawn_stagger_s / connect_stable_s 的存在，都指向同一件事。所以「标定用自己的 recorder 进程」这条路虽然最干净，但要付一次完整 Connect（11 路串行）并重新踩 Argus 不稳定的风险——不推荐，也不需要。

ep_dir 是每个 episode 循环里现算的，START 把完整路径传给守护进程 thor_record.py:1642。换 dataset root 不需要碰 Argus。而且这条路已有现成先例：episode_time:<秒> 就是为这个向导加的、走 side-effect 而不是走 FSM 队列的 stdin 命令 thor_record.py:387。

L0

把意图写进磁盘

前置 · 最便宜

每个 episode 的 meta.json（_write_episode_meta thor_record.py:582）加一个块：

"capture_intent": { "purpose": "calibration_intrinsics", "target_camera": "cam_05", "session_id": "calib_20260902_143012", "protocol": "charuco_400_edge_sweep" }
机制
新 stdin 命令 capture_intent:<json>，在 start 之前设进去，与 episode_time: 同一条 side-effect 通道。
收益
本身不大，但后面每一层都要靠它；并且把「哪段是谁的扫描」从内存挪到磁盘，网关重启不再丢失。
验收
向导录一段后，meta.json 里能读出 target_camera；重启网关后仍在。
L1

采集数据分离

核心

新 stdin 命令 capture_root:<path>，让下一个 episode 写到另一个 root（同样是 side-effect，不进 FSM 队列）。向导在 session start 时指向标定专用 root，session 结束时清空。

outputs/calibration_captures/calib_20260902_143012/ intrinsics/episodes/episode_000000..000010/ → intrinsicsDatasetRoot extrinsics/episodes/episode_000000/ → solveDatasetRoot

一次会话产出两个目录，天然对上解算侧已经存在的那两个指针。配套三处：

  • _dataset_kind gateway.py:1241 加一个 "calibration" 分支——这是现成的按目录归类机制（training_view / exported 已经这么做）。加上之后 gateway.py:6063 那行 != "recorded" 的过滤自动把标定段排除出任务进度和 v3 导出，一行都不用改。
  • _complete_replay_dataset_candidates 要把新 root 纳入扫描，否则 _solve_candidates 的下拉里看不到刚录的标定采集。
  • gateway.py:3647 那段「name is a label and not a path」的 workaround 整段删掉——向导重新成为 dataset root 的真值来源。

Live Record 与标定的解耦到这一层就完成了。进程仍然共用（这是对的，Argus 只能有一个 owner），但数据、命名、统计、导出全部分离。

验收
标定一轮后：任务的 completedEpisodes 不变；v3 导出不含 calib_*；解算下拉能选到新采集。
L2

解算侧按段过滤相机

唯一修正确性的一层

detect_charuco 已经有 --cameras detect_charuco.py:48，但它是全局的，表达不了「episode_3 只取 cam_03」。加一个 --intent-manifest：读每个 episode 的 capture_intent.target_camera，内参 episode 只检测目标相机。

  • 检测 132 → 22 个视频
  • calibrate_intrinsics 的 by_camera 合并问题自动消失——每台相机的 npz 只来自它自己那一段
  • observed_radius_fraction 恢复成「这一段挥得够不够」的诚实判据

代价 01 和 02 只有这一层能修。L3 / L4 只省资源。如果只能做两层，做 L1 + L2。

验收
同一份采集，加 manifest 前后对比每台相机的 observed_radius_fraction：差值就是此前被别段帧顶上去的量。
L3

存储侧剪枝

磁盘 6×

在 online_sync 的同步闸门通过、episode 确认保存之后，按 capture_intent.target_camera 删掉非目标相机的 mkv，并在 meta.json 里记下删了哪些。

必须在同步闸门之后做。missing_frame_policy: fail_episode 和 SOF 全簇对齐（实测偏差 0.008–0.009 ms）需要全部相机在场，提前删会把闸门本身弄坏。

开关
默认对标定采集开启，留一个 keep_all_cameras 退路。
验收
9.90 GB → 1.65 GB；同步报告仍然覆盖全部 11 路。
L4

真正只录目标相机

建议缓议

START <idx> <frames> <dir> [--cams=cam_05]，C++ 侧仍然全簇采集（同步语义不能动），只对子集起编码器 / muxer。

  • 省的是 10 路硬件编码 + NVMM 带宽，而 Thor 有专用编码器，L3 之后这些本来也不构成瓶颈
  • 代价是改 C++、改守护进程协议、重新做同步语义的 burn-in
  • 而且它改变了同步语义的可审计性：现在同步报告能证明全簇对齐成立，子集录制之后这条证据链会变薄

除非实测证明编码器或 NVMM 是瓶颈，否则 L3 之后 L4 的边际收益接近零，风险却最高。

06

已定的三条决策

2026-09-02
✓

非目标相机的帧：不留

L2 过滤 + L3 删除。按指引它们是协议外数据，而现在它们正在静默进入拟合并影响验收判据。保留原始证据的价值不足以抵消这一点。

✓

标定采集落 outputs/calibration_captures/

独立 root，_dataset_kind 一个分支就把任务统计和 v3 导出隔离掉。附带效果：outputs/ 被 deploy 的 --delete-delay 排除在镜像之外，标定采集不会被 deploy 抹掉。

✓

不给标定单开 recorder 进程

Argus 只能有一个 owner，重开一次 Connect 要重新承担 nvargus-daemon 的不稳定风险。换 root 走 stdin side-effect，完全绕开这个脆弱面。

✓

L4 缓议

先做 L0–L3。只有当实测证明编码器或 NVMM 是瓶颈时才动 C++ 与守护进程协议。

08

明确不做的事

不动同步语义

全簇 SOF 对齐和 missing_frame_policy 是所有下游时间对齐的地基。剪枝一律在闸门之后。

不重开 Argus 会话

标定与 Live Record 共用 recorder 进程是正确的——要拆的是数据，不是进程。

不把解耦当成 preflight 的修复

导出器承接不了未重拟相机是独立缺口，单独排在第 4 项，不靠这次改动顺带解决。
