ROI / Camera Crop 的训练-推理合同

2026-08-25 定位失败根因

Training View 的 camera crop 一直是只作用于训练侧的变换。它把裁剪后的像素烘进 view 的视频，view 的 feature shape 就是裁剪框的尺寸，于是 checkpoint 声明要一张只存在于那个矩形里的图；而 rollout 读的是整幅传感器帧，旧代码直接 cv2.resize 到 feature shape，从不裁剪。

侧网络实际看到的
训练 ee = 源帧 [58,194,542,286]、side = 源帧 [108,58,444,382] 这两个矩形内的像素。
推理（修复前） 整幅 640x480 被压进 542x286 / 444x382。日志原文：policy_image_preprocess camera=ee raw_shape_hwc=(480, 640, 3) policy_feature_chw=(3, 286, 542) method=cv2.resize_no_crop

两侧的映射差是一个缩放 + 平移的仿射错位，不是噪声。以 ee 为例，训练是 v = Y - 194，推理是 v = 0.596 Y，在 ROI 顶部错位达 116 px / 286 行（约 40% 图高）。peg-in-hole 的精定位主要靠这颗 wrist 相机，这一项足以单独解释“轨迹形态对、就是伸不到位”。

为什么它一直没被发现：两条路径产出的图像 形状完全相同，都是 policy 声明的 feature shape。没有任何一层会报错——shape 检查通过、rollout 正常跑完、clamp/leash 不触发。唯一的线索是那行 method=cv2.resize_no_crop，以及 manifest 里非空的 camera_crop_specs。

ROI 形状本身不会拉伸图像

pi0.5 侧用的是 resize_with_pad_torch（src/lerobot/policies/pi05/modeling_pi05.py），ratio = max(w/W, h/H) 等比缩放后补黑边，所以矩形 ROI 是 letterbox，不是 squeeze，几何不失真。ROI 的真实收益和代价是有效像素：640x480 等比进 224 只占 224x168，256 个 SigLIP patch 里 64 个（25%）是纯黑；换成接近 1:1 的 ROI 既减少黑边，又把目标线性放大。所以 ROI 值得用——前提是两侧用同一个框。

修复与验证顺序

  1. 确诊。cat <view_root>/meta/il_view_manifest.json | grep -A5 camera_crop_specs 与 rollout 日志的 grep policy_image_preprocess 对照；manifest 有框而日志 raw_shape_hwc 是整幅传感器帧即确诊。
  2. 推理侧补裁剪（已做）。fr3_act_infer_real_runtime.py::load_camera_crop_specs() 从 view manifest 读框，apply_camera_crop() 在 resize 之前取同一个矩形。相机分辨率与录制不一致、或框超出实时帧，都直接 raise——裁剪框是以源像素表达的，换个尺寸它框的就是场景的另一块，绝不允许静默缩放。
  3. 实证闭环。rollout 带 --debug-step0-dump-dir 采一帧，跑 tools/fr3/fr3_compare_live_capture_to_dataset.py，把 live policy observation 和 dataset frame 并排看。每次换 view / 换相机布置后都应作为 preflight 跑一次。
    注意它的 MAE 不能当 crop 的门限。step0 的状态匹配是自证的：T_B_Ws 正是从这一帧观测解出来的，所以转换后的 live state 必然贴着 dataset 起始位姿合同，[START_MATCH]/[FRAME_MATCH] 的 0.1~0.2 mm 是恒等式而非证据；被选中的 dataset 帧只是某条 episode 的近起始帧，物体摆放与现场无关，图像 MAE 因此被场景布置和曝光支配（实测 mae_255≈46~49）。真正的 crop 门限是 rollout 日志那行 crop_xywh 必须等于 manifest、且 cropped_shape_hwc 必须等于 policy_feature_chw（已由 tests/scripts/test_fr3_act_infer_real.py 锁住）；这个工具的价值是把两张图摆在一起看几何对不对——wrist 相机的两根手指是刚性固连的，它们在画面里的位置就是裁剪几何的直读。把它接进 preflight 时修掉了它自己的两处阻塞：帧扫描把 parquet 名写死成六位 file-000000（Training View 建的 view 是 file-000，现改走 infer_runtime._resolve_dataset_data_file），以及 E/I 帧假设段只会重建 ee.*/gripper.pos、遇到 delta_ee_from_prev_cmd 的 prev_cmd.* 直接 KeyError 崩掉（现改为打 WARN 跳过，图像比对照常出）。
  4. 再训。清干净以上后再动训练超参，且优先改 batch 与 LoRA target（见任务清单），而不是继续加 LoRA rank。
同一族的第二处不对称：曝光/增益。fr3_record_config.yaml 把两颗相机钉死在 exposure_us: 15000（ee gain: 70、side gain: 128），而 fr3_il_infer_realsense_camera_config.yaml 两个都没设。这不是“沿用设备上的值”——configuration_realsense.py 写得很清楚：Leaving exposure_us unset does not mean "keep whatever is there"; it means auto exposure is switched back on at connect。所以**每次 rollout 都把相机切回自动曝光**，而整个数据集的立论前提是曝光、增益、运动模糊恒定。附带还把 60 Hz 让了出去：自动曝光在暗处会把曝光拉过 16.7 ms 帧周期，帧率静默下降，正是这份 config 钉 fps 想避免的那种观测滞后。已把两组值抄回推理 config。step0 抓拍里 live 与 dataset 的色彩/对比差异肉眼可见。
训练超参的两个结构性上限（与 ROI 独立，需一并处理）：
  • pi0.5 的默认 LoRA target（modeling_pi05.py::_get_default_peft_targets）只覆盖 action expert 的 self_attn.q/v_proj 加 state/action 投影，modules_to_save 为空——SigLIP 视觉塔和 Gemma 主干完全冻结。视觉 grounding 不适配本场景时，把 rank 从 16 提到 32 是在瓶颈之外加容量。
  • batch_size=2 对 flow matching：每样本随机采一个时间步和一份噪声，单步梯度被采样方差主导，收敛向均值动作（幅度不足、停在分布中心）。仓库没有 gradient accumulation，batch 只能直接调大。

Action 归一化：99.93% 的 loss 花在被锁死的两个轴上

2026-08-25 训练侧根因

fr3_record_config.yaml 的 teleop 段设了 scale_wx: 0.0 / scale_wy: 0.0，roll 和 pitch 被关掉，SpaceMouse 只驱动 x/y/z 加 yaw。于是 delta_ee_from_prev_cmd 的 drx/dry 结构性地恒为零，只剩数值抖动。但 view 的 action 统计是这样的：

drxdrydx / dy / dz
q99 − q011.1e-053.1e-05~4.6e-03
min..max±1.6e-02±1.7e-02~1.3e-02
极值 / 分位带1500×550×~3×

NormalizationMode.QUANTILES 做的是 2*(x - q01)/(q99 - q01) - 1，不 clamp（normalize_processor.py），所以超出分位带的值被线性外推到无界。拿 24945 帧实际动作代进去：

决定定位的三个平移维一共拿到 0.02% 的 loss，两个不携带任务信息的轴拿走 99.93%。这也同时解释了训练日志里 grdn 从第 2k 步起就稳定在 ~100、而 grad_clip_norm 是 1.0——每一步都被裁到单位范数，方向由 drx/dry 的噪声主导。这一项的权重高于 LoRA target 和 batch size。

真机验证：两条 rollout 各自对应一个被饿死的维度

2026-08-25，crop 与曝光都修好之后，用 checkpoint 038000 / 040000 各跑一条 real_once。这两条日志把上表从一个统计论证变成了观测事实。

  • 接近段是好的，安全包络不是原因。两条都从 home（z=0.396）平滑下降到桌面（z≈0.049），480 步全部 status=pass，没有一次 clamp，leash 一次都没触发。
  • 夹爪从头到尾没有闭合过。model_gripper_raw 全程在 0.58–1.17 之间抖动，最低 0.58，从未接近 0（闭合）。gripper_close_below 与 gripper_change_delay 都是 disabled，没有任何 guard 在阻止闭合——policy 输出的是围绕“张开”的噪声，它没有在做闭合这个决策。
  • 输出越界。1.06 / 1.14 / 1.17 都超出了夹爪的归一化范围 [0, 1]，是同一个未 clamp 的归一化在输出侧的镜像。
两个观测到的症状，各自精确对应一个在 loss 里被饿死的维度：平移拿 0.02% → 只学会“大致往下往前”，没学会精确定位；夹爪拿 0.03% → 压根没学。这条链条到此闭合，不需要再往下查。

一个被证伪的预期，记在这里免得重犯：修好 crop 之后曾预期“接近/伸手会明显改善”，实际没有。原因是 crop 修的是感知，而 policy 在平移和夹爪这两个维度上从未获得过学习信号——感知修好了也没有东西去用它。观测侧的合同和训练侧的目标函数是两件独立的事，修好其中一件不会替另一件背书。

选 MIN_MAX 而不是 MEAN_STD。MEAN_STD 把每维的 mean-square 拉平到 1.0（平移合计 42.9%），但 drx 仍留有 88σ 的尖峰，梯度尖刺不会消失；MIN_MAX 按构造把所有维界定在 [-1, 1]，而且死轴的取值被压成一个近似常数（drx 恒在 +0.54 附近），模型几步就拟合掉、此后不再贡献梯度。MIN_MAX 下夹爪占到 51.9% 看着偏高，但它恰好是当前坏得最彻底的那一维，而且是一个真实的双峰信号（mean 0.553 / std 0.489），这个分配是想要的而不是要修的。无需重建 training view——min/max 已经在 meta/stats.json 里，归一化模式是 policy 侧的选择。STATE 侧不要动：那边每一维的极值/分位带比值都在 1.0–1.9，没有这个病。

在训期早停判据，别等四小时：(1) 2k 步时 grdn 应从 ~100 掉到 O(1–10)，还停在 ~100 就是这个判断错了，立刻停；(2) MIN_MAX 下动作有界，loss 绝对值应落在 O(1) 量级，不再是 52–600。

归一化不是根因：契约让 policy 不看图就能答对

2026-08-26 契约根因

界限，写在这里而不是藏起来：这是位姿流形，不是图像流形。两帧可以位姿相同而画面不同，因为销在别处；横向距离小不证明观测在分布内，横向距离大则确实证明位姿不在。这正是 GPU 探针补上的那一半。

(7) 杠杆有个地板：真机延迟是 298 ms，不是 193 ms

执行步数 = chunk_size − replan_queue_size。再规划是异步的（qsize ≤ replan_queue_size 时起 rtc_planner.start，旧队列继续驱动机械臂），所以调大队列是提前再规划、缓冲更多，不是更冒险。但它有上限，而上限是延迟定的。

实测（本卡初稿写错了这一条）：离线单测策略调用是 193 ms，那是裸推理。真机还要抓两路相机、预处理、和机械臂通信。从 rollout 日志自己的 rtc_lat_ms 读（09-22 两批，n=38 次稳态抽样）：中位 298 ms / p90 326 / 峰值 341（冷启动那一次 560 ms，每条 rollout 一次，不是工作点）。

(5) P0 的一次 trial，以及它能说和不能说的

高度按相对量定义：pegRefZ = scene reset 在一根立着的销上的抓取 TCP 高度（放置高度 0.058），dz=0 就是「reset 怎么夹它」；示教合手 51.4 mm 对应 dz=−6.6。销始终在同一张桌上，所以现在内部就是固定世界 z；漏斗读同一个字段，以后 localizer 报出销高时，只替换一个数，不改语义。

一次 trial：在携带高度移到 (spot+dx, spot+dy) 上方 → 以 0.02 m/s 带接触判据垂直下降到 pegRefZ+dz。途中接触则判 contact，不合手直接撤。到位则合手、抬 3 cm、读宽度（阈值 0.025，与抓取循环同一判据）。held 的沿原路放回再松开。之后在标称位姿做一次验证抓取，用的是同一个原语：抓住说明销还立在原处，并且沿合爪方向被重新居中；抓不住则记 pegDisturbed，请人把销放回夹具，由 reset 重新摆到 spot。

一个上机前就知道的坑：本臂下降时有 4.6–5.7 mm 的静摩擦死区。自由下降可能停在设定点上方几 mm，这个残差是固定的、不增长，接触判据看的是增长，所以不会报接触，只会在超出 2 mm 容差后报 timeout。所以 timeout 不判接触，照常合手，停短多少记在 descentShortMm。包络按实测的 closeOffsetMm 读，不按指令偏移读。

四个数字的算法（已被第十四版 (3) 的成功率判据取代；原文：刻意保守，肉眼能对表核对）：XY 捕获半径 = 最大的 r，使 |偏移| ≤ r 的 xy 网格 trial 全部抓住，圈内任何一次失手都会取消这个 r；抓取 dz 区间 = 中心列上、围绕网格高度、全部抓住的连续 dz 段；接触下界 = 中心列上报接触的最高 dz；碰倒半径 = 出现 pegDisturbed 的最小 xy 半径。每点只做 1 次时，这些都是网格的边，不是区间估计，细扫就是为此而设。

(4) A 臂的根因：y 方向往训练数据的中心收

两批里 A 臂合过手的 18 次，合手点对销的真实位置做线性拟合：

轴拟合误差标准差
x合手 x = 0.97 × 销 x + 0.008，基本准13 mm
y合手 y = 0.77 × 销 y − 0.035，不动点 −0.148；corr(销 y, 误差) = −0.7332 mm

训练集里抓取时刻的 y 均值是 −0.155（标准差 80 mm，范围 −0.285 到 −0.013），和不动点几乎重合。策略在 y 上没有真正学会看销的位置，而是往训练时最常见的位置收，少走约 23%：销在 y ≈ −0.04 时它往 −y 偏 11–40 mm，销在 −0.22 到 −0.30 时往 +y 偏 17–74 mm，方向每次都朝中心，没有例外。在空中合手（比销高 2–4 cm）是同一件事在高度上的表现。

为什么会这样：156 条训练 episode 里只有 42 条包含从张开到闭合的抓取，67 条是从已经夹着销开始的。放置区的销离训练抓取中心 63–149 mm，A 是在它最弱的区域被测的。

含义：A 臂靠数据补，重点是 y 两端（y > −0.08、y < −0.22）的完整抓取示教。B 的漏斗只要求策略把末端带到附近，正好绕开这个短板，所以第一阶段的主线是 B。
