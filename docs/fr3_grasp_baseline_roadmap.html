验收发现的缺陷：把瞬时抖动当成了抓取

夹爪指令是连续量，按 0.5 阈值切出闭合区间。旧规则取第一个下降沿，再取其后第一个上升沿。 第 9 轮的指令在 step 388 只掠过 0.4997 两步就弹回，真正闭合发生在 22 步之后 —— 于是那两步成了整段抓取， 一次 lift 73 mm、横移 108 mm 的成功被归档成 lift=0、held_steps=2、抓取点与释放点重合。 同一轮真正的握持本身还被 3 步的越界切成两段。

修法与既有的“抓取是下降沿、不是电平”同一条思路，再推一步：抓取是一段握持，不是一次抖动。 间隔小于 _TRACE_GRIPPER_REOPEN_MIN_STEPS = 5 步的闭合段并为一段，取其中最长的一段作为 这一轮的握持。阈值仍然只是参数，原始 CSV 还在手上，旧 rollout 可以按新规则重算。

第二个缺陷：轨迹文件在会话之间互相覆盖

rolloutIndex 每个交互会话都从 1 重新开始，而轨迹只按索引命名。 今天 15:11 启动的第二个会话，把上午会话的 rollout_001.csv 起逐个覆盖掉了—— 包括上午仅有的两轮成功（第 8、9 轮）的原始轨迹。rollout_log.jsonl 里 (logPath, rolloutIndex) 仍然唯一，所以记录没丢，丢的是可复算的原始数据。 整个约化设计的前提是"轨迹留着，阈值以后还能改"，这个覆盖正好废掉那个前提。
  • 已止损：上午会话的 10 条轨迹从本机副本恢复到 outputs/rollout_traces/session_20260831_033716/。
  • 已加护栏：tools/fr3/fr3_rederive_rollout_geometry.py 检测到日志含多个会话时 直接拒绝执行并列出会话，而不是默认取最新的——否则它会把一个会话的落点写到另一个会话的记录上。 验证过：不带 --session 退出码 2；带上之后精确复现第 2/4/5/9 轮的差异。
  • 待修（S0.3）：轨迹文件名应带会话标识（logPath 的时间戳即可）， 与记录里的 logPath 对齐。在此之前，每批 rollout 结束后先把轨迹目录归档再开下一个会话。

更要紧的一条：握持不等于抓到

第 4、5 轮的人工备注是 push down —— peg 被推倒，没抓住。而这两轮的轨迹是 190 步 / 87 步的连续闭合，末端分别抬升 67 mm 和 79 mm。也就是说：夹爪合拢并抬起，手里可以是空的。 在 xyz + 夹爪指令这个空间里，"抓起来搬走"和"抓空了搬走"完全同形。

observation 侧的夹爪宽度也救不了：取各轮握持段内的非零读数，成功轮中位数 0.0106 / 0.0109 / 0.0133，push down 轮 0.0076 / 0.0079，区间完全重叠，且 9%–48% 的帧是掉线 0。 这条链路没有"手里有没有东西"的信号。

因此：lift、held_steps、释放点都不能单独用来判定成功。 它们记录的是"夹爪在哪里合拢、在哪里张开"，不是"抓到了什么"。 成败标签仍然只能来自操作者的评分，落点图上的抓取点应读作闭合点。 想让几何自己能判成败，需要新的观测（腕部相机的抓后确认、力/宽度阈值、或放置后的物体位姿）， 这是一项独立工作，不在 S0.1 范围内。

真机验收步骤

  1. 先运行相机外参比对，并把结果与本轮 rollout 一起留档。
  2. 同一交互会话启动第一轮：核对 CSV、end marker、评分 JSONL 和地图点一致。
  3. 停止后确认 armAtStart=false；按 Move to start，确认回到数据集起点且夹爪保持不变。
  4. 同一进程启动第二轮，重复检查，证明多轮起点契约成立。
  5. 至少覆盖一次“从未闭合”，确认最低接近点以空心点出现。
通过判据：两轮的四段数据一致、第二轮确实从归位后的起点开始、无闭合分支不产生假抓取点。 在此之前，不用 S0 地图选择 S2/S3/S4。

七、评分机制：阶段，不是分数

先问评分是给谁看的

一个评分只有在改变某个决策时才有价值。这里有三个不同的决策，需要的东西并不一样：

  • 是否达标 —— 需要二元。
  • 下一步修哪里 —— 需要知道在哪一环断的。
  • 补什么数据 / 在哪接管 —— 需要知道当时的状态和原因。

一个 1–5 的分数三样都服务不好。但一个有序的阶段同时服务前两样，因为"成功"不过是 "走到了最后一级"。

第一性原理：操作任务是一条前提链。 每一环让系统获得一个新的物理约束，后面每一环都依赖它。 你观察到的五种情况本身就不是并列的类别，而是这条链上的断点，天然有序： 空抓（没建立接触）→ 推倒（接触了但约束没成立）→ 夹起没插进去（约束成立、目标没对上） → 插一点歪了（目标约束部分满足）→ 完全插入。 评分就是"走到的最远前提"。

三条使用规则

  • 不要求平均。阶段是序数不是间距量：2→3 跨越的是"约束成立与否"，4→5 跨越的是"精度够不够"， 两者不可通约，"平均分 3.2"没有意义。
  • 报告方式是漏斗——达到 ≥ 每一级的比例。二元成功率只是 k = 末级的那一格。
  • 相邻两级之间流失最多的那一格，就是下一个工作项。 这正是第六节的分档表一直想做、但用 lift / held steps 做不到的事。

MuJoCo 交接演练与网页实时视图（已实现）

"先在 MuJoCo 后端把交接跑通"现在有一个具体的东西可跑： tools/fr3/dagger_sim_dryrun.py。它不加载 checkpoint—— 被演练的是交接，不是策略，而一条逐帧回放的 demo 恰好具备交接需要的全部性质： 每帧都出命令、可重复、并且在操作者一动手就不再知道机械臂在哪， 而那正是交还必须挺过去的条件。让策略真的在 sim 里跑，需要仿真把两路相机渲染到可信， 那演练的是渲染，不是交接。

  • 接管期间 demo 流冻结。它是开环的：继续推进就会用一条机械臂已经不在的轨迹算出目标， 交还时相差以米计。冻结之后，交还就是一条回到暂停点的命令，并且走同一套步长钳制—— 机械臂按钳制速率走回去而不是扑过去。走回去的距离记为 handback_gap_mm， 这是演练要产出的那个数。
  • 钳制与控制通道已抽出共享模块（tools/fr3/command_guard.py、 tools/fr3/interactive_control.py）：演练跑的必须是真机要跑的那一份， 两份实现就是在演练一个没人会运行的守卫。抽出来的另一个好处是它们不再依赖策略栈， 可以在这台工作站上直接测（本机导不动 lerobot.policies，见第四节）。
  • 每个控制步要把设备排队的报文全部读干净。SpaceMouse 按 200 Hz 出报文， 而它的两个 scale（translation_scale 0.000615 m、rotation_scale 0.000648 rad）是每报文的量，不是每秒的量。rollout 环跑 30 Hz，一步只读一份报文， 就等于把操作者手上的动作打了三到六折；没读的那些堆在 hidraw 队列里直到溢出， 于是真正读到的那一份已经是将近一秒前的手。同一只手，慢六倍、还迟到、还一阵一阵地来—— 接管手感像在推糨糊，原因全在这里。把一步之内排队的报文累加成一个 delta， 就还原了录制端本来的算术：同样的报文、同样的 scale、同样的每秒距离， 读它的那个环跑多快都一样。
  • 模拟臂不报 prev_cmd，而步长守卫缺了它会退回按实测位姿量步长—— 那把跟踪滞后折进了步长，同一条命令在演练里和真机上会被钳制成不同的样子。 演练把自己上一条已发命令写进那几个字段，值不是编的：那正是真机上这个字段的含义。
网页端实时视图：不再是"先 run mujoco、再 play"。 运行中的进程每步打印一行 live_frame=（七个关节角、夹爪、指令位姿、实测位姿， 以及这一步是谁在开），gateway 收进一个有界环形缓冲，页面每 150 ms 取增量、 按产生时的帧率播放。关节角而不是画面：浏览器已经有这条臂的 FK 模型 （回放视图用的 kinematics.json），七个浮点数比一张 JPEG 便宜得多， 而且发送端不渲染、不编码、不阻塞——一个会拖慢控制环的观察器，就是会改变被观察对象的观察器。 代价是画面比机械臂晚约一个轮询（0.2 秒左右）；换来的是运动是连续的， 而不是每秒五帧的跳格。
页面上没有接管按钮，这是有意的。动一下 SpaceMouse 就把机械臂拿走， 松手静止约 1 秒（--dagger-takeover-release-after-s）策略自己接回去。 按钮是出事那一刻还要去找的第二样东西，而且是会被忘在错误位置的东西—— 上一次 rollout 结束时还锁着接管，下一次就把机械臂交给了一个没人握着的设备。 页面只在运行时自己声明绑定了接管键时提示"SpaceMouse 已就绪"：没有设备时运行时拒绝绑定。 终端的 t（以及同名的控制词）保留为手动锁定，给想让机械臂停住不动的操作者， 不是接管的常规入口。谁在开由实时视图自己的 pill 显示，读的是运行时发出的帧， 而不是页面上的某一次点击——页面和机械臂在这件事上不该有分歧。

接管段写成训练数据（已实现，未上机）

三个决定值得记下来，因为每一个的反面都会安静地产出一份看不出问题的坏数据集。

  • 写的是发出去的命令，不是操作者的请求。存进去的动作是过完 EMA 与步长/牵引钳制、 真正到达机械臂的那一条。这也是录制端自己的约定，但在这里更要紧：专家的原始 delta 经常大于步长守卫允许的量，回归"请求"就是在教策略说一门它自己的运行时听不懂的话。
  • 只写操作者开过的那些步。接管之前的几帧是策略正在出错的那几帧， 把它们一起回归就是在学那个正在被纠正的错误。段边界直接就是 expert_spans 的边界，所以轨迹文件和数据集不可能对"纠正了哪一段"有分歧。
  • 一段一个 episode，而且在 rollout 结束后才写。save_episode 要编码视频， 耗时以秒计；而一段结束的那一瞬间，正是操作者刚松手、策略马上要重新驱动一条真机械臂的时刻—— 整个 rollout 里最不该卡住控制环的一刻。所以接管帧先留在内存里（上限 --dagger-max-buffered-frames，默认 450 帧≈15 秒），机械臂停下来再写。 两段纠正不会被拼成一个 episode：拼接处的两帧相隔数秒、相距数厘米， 跨过它训练就是在学一个机械臂从未做过的转移。
落在独立的 _dagger 数据集里（FR3_DAGGER_DATASET_ROOT）， 不动原训练集：多轮 DAgger 各自成集、随时可丢弃重来，而写进原集是不可逆的。 schema 取自被模仿的那个数据集再加一列 is_intervention—— DAgger 数据只有和示教数据同形才有用；指到一个 schema 不同的老目录会直接报错退出， 而不是照着错的列写下去。

启动器这一侧已经补上：dagger_sim 每次都写 outputs/dagger_sim/dryrun_<时间戳>.json（FR3_DAGGER_SIM_REPORT 改路径）， 报告里连同当次的钳制上限一起记——一个交还距离只有放在产生它的那组上限旁边才有意义， 而启动器传的那组和脚本自带的默认值并不相同。原来这个 --output 要手敲， 于是一次演练做完了，数却没落下来。

两个毛病，同一个根：pyspacemouse 以非阻塞方式打开设备，一次 read() 只从内核队列里取一份报文；队列取空之后， read() 返回的是设备的缓存状态而不是"空"。于是 （一）一步只读一份，设备每秒约 126 份对上 30 Hz 的控制环，每秒落后约 96 份—— 手已经拿开了，队列里还压着一秒前的报文在推机械臂； （二）队列见底以后，同一份非零报文被当成新输入无限重放，机械臂匀速漂走， 而"设备安静够久就交还"的计时器被每一份复制品重置，所以永远等不到交还。

判据先行：当策略的散布已经收到示教的散布，而任务仍然失败时，才轮到 RL。 这不是一个日历上的时间点，是一个可以直接从数据里读出来的量。

为什么是这条判据

模仿类方法（BC、DAgger）的上限是示教者本人的精度——标签就是人的动作，学得再好也只是把人的手复制过来。 这个上限是可以被量出来的：本任务 48 条 demo 的闭合深度 sd 是 3.5 mm，那就是 spacemouse 操作者 在最后几毫米上的抖动。如果精细操作的目标严于这个数，模仿在原理上就到不了， 因为标签自己没那么准。RL 用的是任务定义的回报而不是人的动作，因此可以超过示教者—— 这是它唯一不可替代的性质，也是唯一值得为它付代价的理由。

量现在触发线读法

三个硬前置条件，缺一不可

  • 自动回报——这是最大的一个，而第四节已经证明现在没有。 轨迹分不清"抓到"和"抓空"，成败只能来自操作者。人评 = 每个 episode 按一次按钮 = 上限几百个 episode，而 RL 要 10²–10⁴。需要新观测：腕部相机的抓后确认、 夹爪宽度 + 力阈值、或放置后的物体位姿。 这项工作在第四节里本来就是独立列出的，它不只服务 RL。
  • 自动复位。现在 peg 靠人摆回去。没有自动复位，"多试几次"就等于"多摆几次"， 于是 RL 的样本成本被人力锁死。S0.5 的 record / rollout 场景 reset 按钮就是这项前置工作的最小版本： 固定取料位抓 peg，抓后先抬高 12 cm，再放到 xoy 随机、z 固定的目标区域；区域可由散点图参考加画笔 mask 定义，但采样、限位、日志和失败分支必须在后端闭环。
  • 安全的探索边界。RL 会主动试探没试过的动作，真机上这要求钳制、力限与自动急停先成立。 好消息是第八节的"单一钳制路径"就是同一件事，两条路线共用。

四级阶梯，按代价排序

R1 几乎是免费的，而且它的前置条件恰好是第七节刚落地的东西。 阶段评分把每一条 rollout 变成了一个有序标量——那正是 return 的定义。 所以在这条路线上，"上 RL"的第一级不是一个遥远的大工程，只是训练时多喂一个 token。 代价是一次重训，因此它排在"先不要改权重"这条约束之后。

为什么不能跳过 DAgger 直接做 R1

条件化 token 要学会"高等级长什么样"，前提是高等级和低等级出现在同一片 state 分布里。 现在 29 轮里只有 2 轮成功，正例几乎不存在，token 学到的会是"等级 = 这一小撮特定初始位姿"， 而不是"等级 = 动作更准"。DAgger 的接管数据补的恰好是这一段：同一个失败态上， 既有策略走错的动作，也有人纠正后的动作。所以这个顺序不是偏好，是数据结构决定的。

一个反向的代价，要在动手前想清楚：一旦评分进入损失函数，它就不再只是诊断。 R1/R2 会把 stage 从"给人看的漏斗"变成训练信号。 那时漏评、误评不再只是让分母失真，而是直接改变学到的策略。 因此要上 R1，第七节那条"每轮必评、blocker 如实填"就从建议变成硬要求， 而且需要先做一次评分一致性检查（同一批 rollout 两个人独立评，看分歧率）。
优先级结论：S7，排在 S6 之后，现在不启动。 但其中一项前置工作应当提前开始——自动成败判定（腕部相机抓后确认 / 夹爪宽度 + 力）。 它同时解决三件事：第四节的测量缺口、评分的人力成本、以及 RL 的回报来源。 它不改权重、不改控制环，是这张表上少见的"三条路线共用"的投入。

十、当前不要重开的方向

  • 不给 language model / vision tower 加 LoRA：信息已完好到达 KV cache。
  • 不靠提高 num_inference_steps 缩散布：它只改变 ODE 积分精度。
  • 不做推理端多采样平均：在线成本过高，且 B/C 首要问题是条件均值精度。
  • 不动 rtc_execution_horizon：全量训练后“首步最差”已经自愈。
  • 不基于 drz R² 再调权重：先换成绝对角度误差。
  • 不要给 z 加一个常数补偿来"修"闭合过浅。 回放判别实验已经排除了坐标系漂移，没有一个偏置在等着被补；而常数本来也解释不了散布： +10 mm 只是把分布整体抬高，sd 9 mm 不变，低尾照样闭合过浅。按 (b) 走 DAgger。
  • 不要现在上 RL。策略的散布还是示教的 2.6 倍，缺的是模仿不是超越示教； 且自动回报尚不存在，见第九节。
