fps 契约：导出时统一降采样到 30 fps

训练动作是 delta_ee_from_prev_cmd，即每帧位移。同一段真实速度下，30 fps 的每帧位移是 60 fps 的两倍。把 0813（30 fps）和 0819（60 fps）直接合并进一个 Training View，等于往动作分布里注入一个 2× 的双峰尺度因子，模型无从分辨。

解决方式不是拒绝合并，而是让导出支持指定帧率并对原始数据降采样，默认 30 fps。录制端可以继续用 60 fps 采（时间分辨率更高、QC 的 timestamp_sync 更容易判），训练视图统一落到 30 fps，两批数据就此可合并。

为什么降采样几乎是免费的：训练视图的 mp4 是整段 symlink 的，parquet 行通过 from_timestamp/to_timestamp 按时间戳定位视频帧（fr3_train_il_policy.py:806）。 所以「隔行抽取」不需要重编码视频——保留的行仍然指向 mp4 中正确的时刻，只是行间距变成了 1/30 s。只有在同时启用裁剪 / 缩放（已有 ffmpeg 路径，:397）时才会触发重编码。

降采样的实现约束

  1. 必须先抽帧、再求 delta。derive_delta_action 是对相邻行做差分。若先求 delta 再抽行，被丢弃的那些帧的位移会直接消失，轨迹会缩短一半；先抽行再求 delta，delta 才正确地跨越新的帧间隔。这是整个特性里唯一会静默出错的地方。
  2. 只接受整数抽取比。source_fps % view_fps == 0，60→30 抽 1/2、30→30 不动。60→25 这类非整数比需要插值重采样，应当直接报错而不是就近取帧。
  3. timestamp 保持原值，frame_index/index 重新编号。保留行的原始时间戳本来就是 1/30 s 间距，改写反而会与 mp4 脱钩；而索引列必须连续，否则 frame_continuity 检查会失败。每 episode 的 length 同步更新。
  4. stats.json 重算而非换算。与 fr3_migrate_tool_frame.py 同样的理由：分位数 q01..q99 没有闭式映射。
  5. implied_p95_speed_mm_s 必须用新 fps 计算。否则这个字段会报出 2× 的速度。

GET /api/training/machine		 只用标准库，且远端是把脚本喂给 stdin 执行的——它要回答的问题包括「那台机器上到底有没有这个仓库」， 所以不能假设仓库已经在那儿。报告 GPU（型号 / 显存 / 利用率 / 温度 / 驱动）、torch + CUDA、磁盘、 以及每个策略缺哪些包。没有 torch 时所有策略都判为不可训——act / diffusion 不需要额外依赖， 不这样折算的话，一台刚同步完代码、环境还没装的机器会被报成「可以训 act」。
W&B API key ~/.config/lerobot-gui/wandb_<host>.key
GET/POST /api/training/wandb		 按机器分别存，0600，不回传给浏览器（只回 configured 和后四位）， 也不进命令行——本机走子进程环境变量，远端由一次单独的 ssh 经 stdin 写成对面的 0600 文件。 命令行参数在目标机上是全体用户可读的。
两个只有真跑起来才会暴露的坑，已修：
  • 训练进程原本会被 deploy 杀掉。gateway 用 stdout=PIPE 拉训练输出，于是 gateway 一死、读端一关， 训练进程写下一行就吃 SIGPIPE。而 run/deploy.sh 每次都会重启 gateway——20000 步的任务实测在第 6000 步被这样杀掉。 现在训练进程直接写日志文件，gateway 只是这个文件的读者；gateway 重启后从 outputs/logs/training/current_run.json 认领回这个 run，继续 tail 同一个文件。 实测：重启 gateway 前后 pid 不变（2223337），step 从 2661 走到 3133，GPU 94%。
    认领回来的 run 没有 Popen 对象，所以「停止」按 pid 杀进程组， 「是否已有任务在跑」也必须看 pid——否则重启后可以再起一个，两个 ACT 挤同一张 24 GB 卡，谁都活不下来。
  • 进度条读数原本是错的。lerobot 的日志行用 format_big_number 打步数，第 1300 步印成 step:1K， 按字面读就是 1。页面会卡在个位数一千步再跳一次。现在步数取自 tqdm 那一栏的精确计数 （1300/20000），loss 仍取自日志行——它只在那儿出现。 纯进度条不进可见日志（一秒十三条，会把真正的日志行冲干净），但仍然参与进度解析。

训练不再从 --dataset-root 重建 view：新增 --skip-prepare，直接训一个已经建好并过了 QC 的 view， 相机 / state / action 契约一律取自该 view 的 manifest。这既是远端训练机可行的前提（那台机器只有 view，没有原始录制）， 也避免了对一份 action 已经是 delta 的数据再求一次 delta。 生成的两份配置写在 <view>/runs/<job>/ 下——同一个 view 会被不同策略、不同步数反复训练， 写到 view 根目录会让那里的 inference config 指向最后一个 job 的 checkpoint； 写到训练输出目录则更糟：lerobot_train 见到输出目录已存在且不是 resume 就拒绝启动。

manifest 的 total_episodes = 20；重建位置误差 ≈ 0；excluded_episodes 明确。
Phase 1
修 P0 缺陷
  • 训练入口泛化（P0-2）。
  • 生成配置的相机 / IP 改为派生（P0-3）。
  • 导出加 --view-fps 降采样，默认 30（P0-4）。
Gate
生成配置与 rollout 脚本默认值逐字段一致；--policy 不再是白名单。
Phase 2
ACT 基线闭环
  • 训 ACT，离线评测先判（P1-1），再 smoke → preview → real_debug → real_once。
  • Diffusion 同数据同 seed 做对照（P1-2）。
  • rollout preflight 校验 frame / fps / action contract（P1-3）。
Gate
至少一个 checkpoint 通过 bounded rollout 并可重复；失败能归因到单一模块。
Phase 3
离线飞轮
  • 把 Phase 2 的失败 case 分类（视觉滞后 / 首帧对齐 / IK 不可达 / gripper 时序 / policy 抖动）。
  • 按失败类型定向补采，而不是无差别多采——这是飞轮相对于「再多采一点」的唯一优势。
  • 新 session 走同一 QC → 以 --view-fps 30 导出并合并进 Training View → 重训 → 复评。60 fps 采集的新数据在此自动对齐到基线。
Gate
一轮飞轮闭合，且新 checkpoint 在原失败 case 上有可测量的改善。
Phase 4
VLA 扩展
  • 装 policy extras（P2-1），先 SmolVLA（P2-3）。
  • 多任务采集（P2-2）——没有这个，VLA 的语言通道是常量。
  • 显存 / batch / 吞吐实测入表，只记本机数据。
Gate
SmolVLA 在同一 Training View 上完成训练并通过离线评测；与 ACT 基线可比。
Phase 5
DAgger / 在线
  • 把 hil_processor.py / gym_manipulator.py 的 intervention 接到 FR3 rollout 控制环。
  • 接管段自动标记为高价值样本，回流走同一 QC。
  • 再往后才谈 reward model（sarm）与在线 RL（sac / hilserl）。
Gate
接管切换不产生轨迹跳变；接管数据在 manifest 中可区分于常规演示。
为什么 DAgger 排在 Phase 5 而不是更早：DAgger 的价值是「用专家纠正 policy 自己走到的 state 分布」，前提是已有能跑出有意义 rollout 的 checkpoint。 Phase 2 之前没有这样的 checkpoint，此时开 DAgger 只会退化成普通遥操作采集，却要付出改造控制环的代价。 反过来说，一旦 Phase 2 完成，DAgger 的边际收益会明显超过离线补采——20 episodes 的 BC 几乎必然存在 distribution shift。
