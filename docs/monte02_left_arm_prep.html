结论

这条路走得通，原因是末端同构。手持采集器的末端，和 Monte02 手臂末端用的是同一套厂家模块：六维力 link_l_sensor_ft、夹爪 gripper_w_v2、指尖 tip_ldt_2gripw_v1（box_cad/urdf/left_end.urdf 就是 Monte02 左末端拆出来的那一段）。11-16 定的相对 TCP 规格（策略只看 T_t⁻¹·T_{t+k}，注册边不进控制回路）本来就不依赖哪台臂，换成 Monte02 时策略和训练代码都不用改，要改的是执行层。
会卡住的四件事，现在就要开始：
  1. 末端相机不一定同构。策略的第一个输入是 cam_10：手持采集器上的相机，走 Thor 的 GMSL2，是 Thor 的一路通道。Monte02 腕部是 tcam_s_v2 RGBD 模组，接在机器人自己的电脑上。两者的传感器、镜头、曝光、时间戳很可能都不一样，要决策（M0.1）。
  2. 腕部限位窄。左臂 j6（腕 pitch）和 j7（腕 roll）只有 ±90°，FR3 的 j7 约 ±166°。人手持采集器时手腕常常转得很大，所以先拿现有左手数据离线算一遍可达性（M2.2），再决定怎么录。
  3. 臂的基座会动。左臂基座 link_l0_arm_base 装在胸上，下面是腰的 3 个关节（膝 pitch、髋 pitch、腰 yaw），再往下是轮式底盘。replay 和 rollout 时这几个关节要锁在固定姿态，底盘要抱闸，每停一次车都要重新注册（M0.3、H 线 H2）。
  4. SDK 只有 Python 3.10 的包。厂家源上只有 cp310 的 wheel（2.2.6、2.2.7，分 x86_64 和 aarch64），Thor 的网关跑系统自带的 Python 3.12。Monte02 的执行层只能作为单独的 3.10 进程运行（M7.1）。
现在就能做、不需要硬件的（详见前置清单）：模型入库并加上和 FR3 同一个点的 socket_ee；不限臂型的 URDF 运动学；MuJoCo 模型和胶囊碰撞模型；拿现有左手数据扫腰姿态和停靠位做 IK QC；在本体描述文件和臂登记表里加 Monte02；按现有 ArmIO 协议写 Monte02Arm 适配器（只用假的 RobotLib 测）；夹爪、外力、触觉的单位映射；时钟对齐方案；把 Monte02 接进沙箱硬件守卫和硬件租约。硬件到货当天要做的检查也可以先把只读脚本写好。

附 A · 《Monte02 操作接口说明 V1.0》要点

安装与连接

  • 推荐 Ubuntu 22.04，依赖 gRPC。两种装法：一是 apt 装 deb 包（corenetic-robot-hardware-api，示例版本 2.2.6，装到 /opt/corenetic/lib，头文件 robot_hardware_api.h）；二是 pip 装 robot-hardware-api（源 pypi.yuanluo.cloud）。机器人本体上已经全局装好。
  • Robot("192.168.11.3:50051", appName, "")：192.168.11.3 是机器人 x86 的有线地址，无线时换成无线地址。每个进程只能实例化一个 Robot，appName 不能和别人重复。
  • 控制臂之前固定要走这几步：使能（set_arm_enable）→ 设模式（set_arm_mode：1 伺服，2 关节拖动示教）→ 设状态（set_arm_state，Monte02 一律设 0）。
  • component_type：1 左，2 右（calib_force_bias_and_load 里 5 表示双臂）。位姿都是 [x,y,z, qw,qx,qy,qz]，单位米。不带 _in_base 的是臂基座系，带的是机器人基座系；关节接口没有这个区分。

运动接口（全部会动臂，agent 不得调用）

接口空间规划说明
set_arm_servo_angle(ct, q7, speed, acc, wait)关节底层规划低频；speed/acc 只是上限
set_arm_servo_angle_j(ct, q7, …)关节不规划高频伺服，要先切伺服模式；speed/acc/wait 目前无效，“以最大速度和加速度到位”
set_arm_end_pose(_in_base)(ct, pose)笛卡尔不规划内部 IK 后调 _j；要求上层规划，100–200 Hz 调用，每步不能太大
set_arm_position(_in_base)(ct, pose, speed, acc, wait)笛卡尔规划直线，速度 0.03–0.1 m/s；wait 取 0 或 2
set_arm_waypoint(ct, mode, wps, …, type, max_deviation)关节或笛卡尔规划平滑路点；type 0 表示从当前位置起步
set_robot_servo_angle(q19, …)全身 19 轴规划19 个值要一起给
set_trunk_* / set_head_*腰 / 头profile 或 servoJ腰有 set_trunk_joint_mode（0 profile，1 servoJ）
set_chassis_velocity(v, w)底盘—每次调用生效 1 s，调用频率至少 1 Hz，否则停车
导航 start_navigation / navigate_to …底盘—navi_mode 2 表示看 AprilTag 精定位；回充 / 离桩

状态、夹爪、力、安全

  • 读状态：get_arm_servo_angle、get_arm_joint_state（位置、速度、加速度、力矩各 7 个）、get_joint_state(ids)、get_robot_joint_state（19 个）、get_arm_end_pose(_in_base) / get_arm_position(_in_base)。文档里这些接口都没有时间戳。
  • 夹爪：set_gripper_enable；set_gripper_position，范围 [0, 0.1] m；get_gripper_position 返回位置和电流力矩，一代范围 0–0.094，二代 0–0.089；set_gripper_effort 一代 0–15 N·m，二代 0–20 档；find_gripper_home 找零位，约 3 s，期间不能碰夹爪；触觉有 calib_gripper_sensor、set_gripper_sensor_status、get_gripper_touch_net_data（2 片的合力 xyz）、get_gripper_touch_tac_data（A、B 两片，每片 9 点 × xyz）。
  • 六维力：get_force_sensor_data 和 get_filtered_force_sensor_data 给 [fx,fy,fz,mx,my,mz]；get_force_sensor_wrench_bias 只读 YAML 里存的零偏；calib_force_sensor_bias 要求静止、负载已经辨识过；calib_force_bias_and_load 会按配置执行默认动作，臂会动。
  • 安全：set_soft_emergency_stop(1/0)；get_emergency_stop_state 的位 0 是硬急停、位 1 是软急停；get_arm_err_warn_code / clear_arm_err_warn_code；get_sys_err_warn_code 在 2.3.0 上总是返回 False。组件控制模式（set_component_control_mode）：1 控制，2 导纳；大于 20 的模式由机器人自己切换，用户不能设。

附 C · 《URDF 可视化配置上位机 1.3.0》（Modeling Zoo）要点

  • 用途：在厂家的上位机上，按模块（躯干、左右臂、TCAM 相机、TOOL 夹爪、TIP 指尖，QCHG 快换可以不装）拼出整机 URDF，合入单台的标定，再发布到机器人用的目录。用浏览器打开 http://<上位机IP>:18763。“机器人名称”决定包名，例如 monte02_h_v1_description，网格路径写成 package://monte02_h_v1_description/…。
  • 操作顺序：选模块 → 用系统密码解锁（默认用户 corenetic）→ 保存并融合（产物在工作目录）→ 检查结果 → 发布（只拷贝文件，不重新融合）→ 检查发布结果。
  • 相关路径（以界面上“配置来源”显示的为准）：整机配置 …/modeling_zoo/tools/config/robot_definition.yaml，流水线配置 …/step02_create_complete_urdf/pipeline_config.yaml，标定状态 /home/corenetic/robot_workspace/config/calibration/calibration_status.yaml。
  • 标定合入：calib_files、calib_file、calib_dir 三选一；多文件只能在高级 YAML 里配。merge_calib_files.py 会核对部件位置、完整型号 metadata.component_model_id（比如 tcam_s_v1 和 tcam_s_v2 算不同）、关节名和数值参数。
  • 结果的含义：CALIB 表示这个部件的标定合并成功了，但不代表精度已经核实；THEORY 表示用的是理论参数，标定没有生效；“退出码 0”只说明进程正常结束；“发布一致”只说明工作区和发布目录的文件相同。这三样都不能当成“标定正确”。状态文件里留着的旧 CALIB，也不能证明这一次融合成功了。
  • 对我们的意义：
    • 我们的 FK 必须用机器人上发布出来的那份 URDF，并且记下它的指纹，以及每个部件是 CALIB 还是 THEORY（H-2）。box_cad 里那份是 THEORY，只能当占位。
    • 末端换了东西（装 pivot 插件、加 GMSL2 相机支架、换指尖），都要先有对应的模块，再重新融合。这一步由厂家或维护者在上位机上做，agent 不做；SDK 里的 execute_urdf_fusion 也一样不碰。
    • 提议的门禁（由维护者决定）：左臂链上只要有部件是 THEORY，或者 URDF 指纹和登记的不一致，就拒绝真机 replay 和 rollout。
    • 11-24 重新评估：上位机本身不做标定，只是拼模块、合并已有的单台标定文件（关节的 xyz/rpy），惯量还是模块理论值，所以称重（T1′）不能省。TCAM/TOOL/TIP 必选而库里没有 GMSL2 支架，因此流程定为：发布的 URDF → build_gmsl2cam_urdf.py → build_mjcf.py → 胶囊重拟合 → 本体文件、白名单重新验证。CALIB 的精度由我们用相机跟踪 rig 和 pivot 自己核。详见 roadmap H-2。

安全（提议加进 AGENTS.md 第 4 节，由维护者决定）
