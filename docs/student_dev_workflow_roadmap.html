学生开发流程路线图

2026-11-10 · 目标：学生拿到完整代码，在自己的分支上借助 AI（Codex / Claude Code 等）实现想法，在 Thor 沙箱里试跑；维护者只审 PR、发版，不再替人部署和排错。

0 · 原则

  • 开发、试跑、生产三层分开。本地开发不碰 Thor；Thor 上每人一个沙箱；生产只跑审核合并后的 origin/box。
  • 门禁放在学生代码之外。学生（和他们的 AI）能改分支里的任何检查，所以真正的边界必须在操作系统、网络、GitHub 设置这些分支改不到的地方。代码里的守卫只防误操作。
  • 可变状态不放在代码树里。部署是"把部署人的工作区镜像过去"，树里只要有现场写入的文件，就会被旧树覆盖。

1 · 第一阶段（已完成，2026-11-10）

  • AGENTS.md（Codex 直接读取；CLAUDE.md 用 @AGENTS.md 引用同一份）：开发流程、沙箱用法、安全红线、踩过的坑、何时找维护者。
  • Thor 个人沙箱：bash run/deploy.sh thor --sandbox <名字> → /home/nvidia/sandboxes/<名字>，端口 8770–8799 自动分配并固定。网关 --sandbox 对所有碰硬件的接口（录制、预览、BOX、激光跟踪仪、真机回放、机械臂、pivot、负载、标定采集）返回 409；离线功能（轨迹生成、IK QC、MuJoCo、导出、回放查看）可用。GUI 顶部黄条标明沙箱和 commit。2026-11-10 实测：部署、复制数据集、二次部署（端口不变、只重启自己）、MuJoCo 预演通过、删除，生产网关全程不受影响。
  • run/sandbox.sh：list / status / datasets / copy-dataset（复制不链接，保证 Thor 留 30 GB）/ logs / stop / remove。
  • 部署只停自己的进程：原来 deploy 会杀掉全机所有网关和录制器（沙箱一部署就会把生产停掉），现在只停同目录或同端口的网关；只有生产部署才停录制器。
  • 生产部署守卫：代码树必须干净、HEAD 必须已在 origin/box，否则拒绝；--maintainer 只放行"尚未合并"，不放行脏树；-n 预演只警告。每次部署写 DEPLOYED.json，快照 deployment.release 可见版本和部署人。
  • CODEOWNERS（部署脚本、FR3、world/标定、label provenance、网关需维护者审核）和 box PR CI（.github/workflows/box_checks.yml：网关 / Thor / FR3 测试 + 前端类型检查和单测）。

第一阶段要生效还需要的手工设置

  • GitHub：box 开分支保护（必须 PR、Code Owners 审核、Box checks 通过、禁止 force push）。仓库是公开的、box 当前没有保护，不开保护时"在 origin/box 上"这个守卫没有意义。
  • GitHub：两个私有子模块各一把只读 deploy key（标题 “lerobot CI (box_checks, read-only)”），私钥存在 secret SUBMODULE_KEY_OPENCV_KALIBR、SUBMODULE_KEY_BOX_SDK；轮换方法见 .github/workflows/box_checks.yml 文件头。缺任一个，CI 拉不到子模块、测试会失败。
  • GitHub：把学生加为协作者（推自己的分支需要写权限）。
  • Thor：学生公钥加到 nvidia 账号；确认学生电脑能访问 Thor 的 ssh 和 8770–8799 端口。

第一阶段的已知缺口（第二阶段解决）

  • 学生和生产共用 nvidia 账号：能 ssh 就能手工 rsync 覆盖生产，守卫挡不住故意或 AI 自作主张的绕过。
  • 沙箱"不碰硬件"写在沙箱自己运行的代码里，分支删掉就失效。
  • 需要硬件的功能学生无法自测，只能交给维护者试。
  • 沙箱的标定是首次部署时复制的快照，之后不跟随生产更新；world 文件来自学生自己的树。
  • gateway.py 整个文件归维护者审核，大部分 PR 都会落到维护者身上。

2 · 第二阶段分项

P2-1学生独立 Linux 用户（真正的写权限边界）

  • Thor 上建学生账号（每人一个，或共用 lerobot-dev，见待决策 1），学生只拿这个账号的 ssh。nvidia 的 authorized_keys 只留维护者。
  • 生产树 /home/nvidia/lerobot 对学生不可写；沙箱移到 /home/<学生>/sandboxes 或 /srv/lerobot/sandboxes（THOR_SANDBOX_BASE 一处改）。
  • 共享只读资源要能被学生读到：/home/nvidia 现为 750，venv（/home/nvidia/Code/infer/.venv-fr3、opencv_kalibr/.venv）和生产数据集都读不到。方案：venv 挪到 /opt/lerobot/venvs，数据集和标定加只读组 lerobot-data。
  • 验收：学生账号 touch /home/nvidia/lerobot/x 失败；run/deploy.sh thor（生产）以学生身份失败于权限而不是脚本；沙箱部署、复制数据集、MuJoCo 照常。

P2-2硬件访问在系统层隔离

  • 网络：iptables -A OUTPUT -m owner --uid-owner <学生> -d <网段> -j REJECT，覆盖 FR3（192.168.1.0/24 右臂、192.168.11.0/24 左臂）、BOX 网段、激光跟踪仪。规则随开机加载（netfilter-persistent）。
  • 相机：查清 nvargus-daemon 的访问控制（socket 权限 / video 组），让学生账号打不开 Argus。需要单独调研。
  • 验收：学生账号下 ping FR3、BOX discover、gst Argus 预览都失败；生产网关不受影响。

P2-3硬件占用锁（让沙箱在受控条件下用硬件）

  • 共享目录里一个租约文件（如 /srv/lerobot/state/hw_lease.json），资源分 cameras / box / laser_tracker / fr3_left / fr3_right；记录持有者（网关目录、端口、用户）、开始时间、心跳。
  • 持有者每 10 s 心跳，60 s 无心跳自动释放；生产网关同样遵守（Connect 前申请，Exit 时释放）。
  • GUI 顶栏显示每项硬件当前归谁、用到几点；被占用时按钮置灰并说明。
  • 沙箱用硬件需要维护者给该学生授权（与 P2-1/P2-2 配合：授权 = 临时放开该用户的防火墙规则），机械臂仍需 MuJoCo 通过 + 有人守急停 + 推理解锁文件。
  • 验收：生产录制中，沙箱 Connect 被拒并显示占用者；生产网关被 kill -9 后 60 s 内锁自动释放。

P2-4可变状态移出代码树

  • 新建状态目录（如 /srv/lerobot/state，环境变量 LEROBOT_STATE_DIR），所有读写经一个解析函数；git 里只保留默认值和历史快照。
  • 迁移时双读：状态目录有就用状态目录，没有回落到树内文件并告警；生产迁完后删掉回落。
  • 沙箱对状态目录只读（P2-1 的权限保证），需要改 world/标定的实验在沙箱自己的副本里做。
  • 验收：从任意旧分支部署生产，world、标定指针、d_box 表都不变；sync_to_target.sh 里"保留 Thor 上更新的 world 文件"那段逻辑可以删除。

P2-5发版自动化

  • run/release.sh（维护者用）：确认在 box 最新提交、CI 绿、树干净 → -n 预演摘要 → 确认 → 部署 → 学生前端自动切到同版。
  • 学生前端改为读 Thor 的 DEPLOYED.json 自动固定版本，不再手动传 commit。
  • 之后可以改成打 tag（如 release-20261120-1）触发；部署前检查当前没有录制和真机回放在进行。
  • 发版后在群里自动通知版本和变更列表（已有 Feishu 通知工作流可复用）。

P2-6机器人运动服务（中期）

  • 把真机运动（回放、move-to-start、推理执行）做成常驻服务，始终跑已发布版本；网关和学生代码只能通过接口提交"计划"，服务里做限幅、工作空间检查、MuJoCo 结果核对、急停确认。
  • 这样分支里删掉检查也绕不过去；与训推路线图的 L3 放行记录合并设计（见 docs/fr3_train_infer_gui_roadmap.html）。

P2-7CI 与评审负担

  • CI 扩充测试集；对改动行跑 ruff check；PR 模板加"是否碰硬件 / 安全门禁"勾选。
  • 把 gateway.py 里硬件接口和门禁拆到单独模块，CODEOWNERS 只管这些模块，其余 GUI 功能可由高年级学生互审。

P2-8文档与上手

  • 学生上手清单：账号、ssh、clone、子模块、本地环境、第一次沙箱部署、提 PR，一个标准练习任务。已完成：docs/student_onboarding_checklist.html（2026-11-11）。
  • 使用指南加"开发者"一节链接到 AGENTS.md 和本页。

3 · 建议顺序

  1. 先把第一阶段合进 box，并完成 GitHub / Thor 的手工设置（小范围试用）。
  2. P2-1 + P2-2（账号与硬件隔离）：开放给更多人之前必须完成。
  3. P2-4（状态移出代码树）：沙箱和发版一多就会出事，排在硬件锁之前。
  4. P2-5（发版自动化）。
  5. P2-3（硬件占用锁）：学生需要自测硬件功能时再做。
  6. P2-6 / P2-7 / P2-8 穿插进行。

4 · 需要拍板

  1. 学生账号：每人一个 Linux 账号（可追责、可单独授权硬件），还是共用一个 lerobot-dev（管理简单）？
  2. 状态目录放哪：/srv/lerobot/state（需 sudo 建）还是 /home/nvidia/lerobot_state？
  3. 沙箱是否最终允许用硬件：如果永远不允许，P2-3 可以只做生产内部的互斥，不做授权。
  4. 发版节奏：固定时间（如每周两次）还是合并即发？
